# Research: where the Nord Stage 4 organ tone is generated (tonewheel bank hunt)

- **Checked:** 2026-11-12
- **Sources (local, never committed):** the five DSP images of OS v1.66 (`python tools/ns4_dsp_images.py target/fw_unpacked/bank0_CODE.bin --out DIR`), flat SRAM images per core (`tools/ns4_dsp_ldr.py DIR/dsp_image_<i>_<NAME>.bin --sram SRAM`, SY1SY2 and SMP via `tools/ns4_dsp_raw.py --sram`), ADI `elfdump` listings of them (`tools/adi_dis.py`, listing address 0 = pc `0x120200`), `target/fw_unpacked/bank0_CODE.bin` (ARM, loads at `0xC0000000`, `tools/arm_xref.py`), `Nord Stage 4 Factory Restore RevK v1.66.ns4b` (zip directory), the User Manual v1.6X, `sharc-run` (`nord-sharc`, `origin/main` fa20ddf). Builds on [org-dsp-map](org-dsp-map.md), [pno-dsp-map](pno-dsp-map.md), [sy-dsp-map](sy-dsp-map.md), [sharc-sy1sy2-smp](sharc-sy1sy2-smp.md), [arm-dsp-protocol](arm-dsp-protocol.md), [dsp-image-hunt](dsp-image-hunt.md) and the ORG stage map of PR #60 (`origin/research/org-stage-selection`, `docs/research/org-stage-map.md`, not yet on `main`).
- **Question:** Where are the organ oscillators (tonewheels, drawbars, key contacts, click, vibrato) computed: in the ORG program (Core1 and Core2), in another image, in data tables, on the ARM, or are organ tones sample based?

Tags follow `.agents/rules/provenance-in-code.md`: **VERIFIED** = reproduced by a command shown here, **EMPIRICAL** = structural shape of code or data, **ASSUMED** = reading of a purpose.

## 1. Short answer

| Question | Result | Status |
|---|---|---|
| Is the B3 tone sample based? | **No evidence for it, and the manual says model.** The `.ns4b` has no organ-section audio (64 `.ns4o` presets of 183 bytes; the `Organ` folder of the sample library holds 6 pipe/flute samples for the **Synth** section); no DSP image carries a large audio table (largest data per image is the 8,192-word table of section 3); the manual describes a digital model ("91 spinning discs", contact bounces, energy robbing, scanner). | VERIFIED (absence), manual quoted |
| ORG Core1, ORG Core2, PNO Core2 | One program: below the start-up code (`pc < 0x125A00`) **10,296 instruction slots, 0 differ** between the three sections. Start-up code differs only by core constants (`ustat1 = 0x200C0000` / `0x20080000`, mailbox, call order). So Core1 adds nothing new: it is the channel-strip / coefficient engine of PR #60. | VERIFIED |
| Does that program hold oscillators? | **No.** No phase-accumulator loop, no sinusoid or note table, no sin polynomial, no 91-iteration loop (loop counts in the program: 2, 3, 4, 7, 8, 12, 24, 25, 99/100, 120, plus data read as code). Its `pi` and `1/(2 pi)` immediates sit in filter-design code (`tan` polynomial and `recips`), not in a sine. | VERIFIED (scans of section 2) |
| **Where is a tonewheel-like bank?** | **PNO image, Core1 section** (`entry 0x121007`), routine at **pc `0x122620`**: 92 wavetable oscillators per frame, `phase += inc`, 12-bit index `fext`, 4,096-point table with **two interleaved waveforms** at `DM 0xC042B`, increments in a 92-entry table at `0x955B6` that the **ARM writes** (section 4). The first waveform is exactly `sin(t) - 0.1122 cos 2t - 0.01585 cos 3t - 0.00631 cos 4t - 0.00398 cos 5t` (-19, -36, -44, -48 dB). | VERIFIED (code, table, oracle run, ARM writer); role "B3 tonewheel generator" ASSUMED |
| Drawbars, key contacts, click, vibrato in that image | Not wired to anything named drawbar or key; the code after the bank is a weighted sum (`pm` weights) and a triangle-LFO delay-line stage (scanner-like). Weights and increments are written at run time by the ARM, so the image alone does not show them. | EMPIRICAL |
| Confidence | That the 92-oscillator bank at `0x122620` is the B3 tonewheel generator: **about 80 %**. That organ tones are neither sampled nor generated by the ORG strip image: **about 90 %**. That Vox, Farf and Pipe models use the same bank: **unknown** (one table pair only). | ASSUMED |

Sine-recurrence detector validated on a synthetic sine (`tools/tests/test_organ_tonegen_census.py`); smooth curves (period far longer than the window) are rejected by design. A scripted scan of all `=0x........` immediates of the ORG, PNO and SY listings for float `2 pi`, `pi/2`, `1/6`, `1/120`, `1/5040`, `ln 2`, `log2 e`, `2^(1/12)`, `440`, `261.6256`, `8.1758`, `27.5`, `32.7032`, `1/48000`, `2 pi/48000` (relative tolerance 2e-6) found only `pi` (`0x40490FDB`, `0x40490FD0`) and `1/(2 pi)` (`0x3E22F981`) in the ORG program, at `listing 0xC17..0xC2D` and `0x35C0..0x35F0` / `0x23C9`: filter-coefficient code (a degree-4 polynomial `0.4936, -1.4645, 1.8442, -0.6035, 1` followed by `recips`, ASSUMED a `tan` or warp approximation).

The ARM image holds two function-pointer tables for the ORG program (VERIFIED, `bank0_CODE@0x2FA050`, 74 words, and `@0x2F72F0`, 7 words): **74 of 74** and **7 of 7** ids land on a non-nop instruction start of the ORG listing, against 27 of 74 and 3 of 7 for PNO Core1 (chance level), so these are the module ids the ARM installs into the ORG strips (`0x12549D`, `0x125B79` of PR #60 are in the second table, with seven parameter triples `0.85 1.0 1 / 1.8 0.6 1 / 3.0 0.4 1 / 0.9 0.46 1 / 1.5 0.28 1 / 2.5 0.17 1 / 4.0 0.16 ...` before it, ASSUMED vibrato/chorus or rotary presets). The palette spans pc `0x120CD0 .. 0x125335`: filters, delays, gains. None of the 81 ids is an oscillator by the scans above.

## 3. The oscillator bank in PNO Core1 (VERIFIED)

Listing excerpt (`python tools/adi_dis.py SRAM/core1_sram.bin 0x240400 ...`, pc = listing + `0x120200`):

```text
122620  r4 = DM(0xC27C5)                      ; 0x40000000 in the image (fractional 0.5)
122627  i2 = 0xC042B                          ; table base: 4096 interleaved (x, y) pairs
12262E  i3 = 0xC24E5   i4 = 0xC2655           ; output arrays, one frame = 0xB8 = 184 words each
122634  lcntr = 2, do ...                     ; two frames per call (stride i3 += 0xB8 at the end)
122637    i11 = 0xC242D   i12 = 0x955B6        ; phase state (PM) and increment table (PM)
122641    r11 = 0x314                          ; fext: 12 bits at position 20 = top 12 bits of the phase
122643    r1 = pm(i12)  ; r1 = r1 * r4 (ssfr)  ; increment * 0.5
122648    r2 = r0 + r1  ; r0 = fext r2 by r11  ; phase += inc, index = phase >> 20
12264C    m3 = r0 + r0                         ; word offset 2 * index (x at +0, y at +1)
122656    lcntr = 0x5B, do ...                 ; 91 iterations + prologue/epilogue = 92 steps
122659      r2 = r0 + r1, pm(i11,m12) = r2     ; store phase
12265C      r0 = fext r2 by r11, r5 = dm(m3,i2); r6 = dm(m4,i2)   ; table read, both waveforms
12266B      dm(i5,m2) = r5 ; r1 = pm(i12,m10)  ; store x, fetch next increment
12266E      r1 = r1 * r4 ; dm(i6,m2) = r6      ; store y
122683  i3 += 0xB8   i4 += 0xB8
12268C  rts (db)
```

| Fact | Evidence | Status |
|---|---|---|
| It is a phase-accumulator wavetable bank: `idx = (phase + inc * 0.5) >> 20`, `out = table[2 idx]`. | `sharc-run SRAM/core1_sram.bin 0x122620 4000 --poke 0:0x955B6+k=(k+1)*0x1000000 --set M2=1 --set M10=1 --dump 0xC24E5:16`: eight outputs `be0108d5 bde89314 bdced813 bdb4e1d6 bd9ab1a3 bd8048d2 bd4b51a5 bd15a64a` = `x[8(k+1)]` (`x[8] = -0.1261`), 1,513 steps per call, halts at the `rts (db)` (unimplemented without a caller, `pc 0x12268c`). | VERIFIED |
| 92 steps per frame, 2 frames per call. | Arrays advance `0xB8` words per frame; the loop is 91 iterations plus the pipelined first and last step. The follow-up routine at pc `0x12268F` (`lcntr = 0x2D` twice) is a dot product over the same 92 elements. | EMPIRICAL |
| The table is 4,096 pairs at DM `0xC042B .. 0xC242A`, initial data of the image (the phase block starts at `0xC242D`). | 8,192 words, wrap step `x[4095] -> x[0]` 1.5e-3 (smooth), 0 outside. | VERIFIED |
| Waveform x is a **designed** harmonic mix: `x(t) = sin t - 0.1122 cos 2t - 0.01585 cos 3t - 0.00631 cos 4t - 0.00398 cos 5t`, `t = 2 pi i / 4096`. | `python tools/organ_tonegen_census.py harmonics SRAM/core1_sram.bin 0xC042B`: harmonic levels `0, -19.00, -36.00, -44.00, -48.00` dB, higher harmonics below -170 dB; direct evaluation of the formula above against the table: max error 1.2e-7 (float32 rounding), peak 1.106. | VERIFIED |
| Waveform y has 10 audible harmonics. | Levels `0, -6.2, -13.6, -21.4, -24.8, -30.0, -33.3, -36.2, -38.7, -40.4` dB (round tenths), peak 1.0, h1 phase 100 degrees, 5-harmonic reconstruction residual 0.020. | VERIFIED (spectrum), role open |
| Increments are not in the image. | `DM 0x955B6..` is zero in the image; the ARM fills them (section 4). | VERIFIED |
| The bank feeds a weighted sum and a scanner-like stage. | Routine `pc 0x12268F`: `f2 = x * w1 + y * w2` per element stored to `pm(i10)` (a per-element blend of the two waveforms with run-time weights), then `lcntr = 0x2D` loops summing `sum * pm(i9)` weights into two lanes, a short filter, `dm(i0) = r0` to the ring `DM(0xB33C0)`. Routine `pc 0x12272D`: triangle LFO (`|phase| - 0.5`, `*4`, clip), `fix`, 65-point style lookups at `0xE22B2` / `0x95CC6`, 19-iteration delay-tap loops. | EMPIRICAL |

Reading (ASSUMED): `x` is the ideal B3 tonewheel wave, `y` a second wave (worn wheel or another model), the 92 elements are the 91 tonewheels plus one spare, the weights are the drawbar x key-contact matrix the ARM computes per layer (the two SIMD lanes could be Layer A and Layer B), the blend `w1/w2` is the tonewheel mode (clean / worn). The count 92 sits one above the manual's 91 discs; a 88-key piano partial bank would be 88 and would hardly carry a -19/-36/-44/-48 dB wave (ASSUMED).

**Not established:** which Nord model uses `y`; whether Vox, Farf and Pipe use the bank; how the ARM schedules the call (no data pointer to `0x122620` exists in the image or in `bank0_CODE`/`bank1_CODE`; the pno-dsp-map module chain is empty in the image and installed at run time); whether this section is physically the organ chip (the names `FX, PNO, ORG, SY1SY2, SMP` come from the ARM name array, ASSUMED to match the images).

## 4. ARM side (VERIFIED where marked)

- ARM function `0xC022A9A8..0xC022AA14` (`arm_xref.py dis`): for group id 2 it writes the DSP word `DM(0x955B6 + index)` with `value << 8` through the DSP write object (`0xC055B150`, register `+0x44`; the address is shifted left by 2 for the byte window); `0xC022A8A4` returns `0x5C = 92` (item count); `0xC022A87C` returns `0xC24E5` for id 4 and `0xC2655` for id 5 (the two output arrays). Literal pools: `0x955B6 @0xC022AA38`, `0xC24E5 @0xC022A8A0`, `0xC2655 @0xC022A89C`. So the ARM supplies 92 phase increments (24-bit, `<< 8`) and knows the output arrays of the same bank. VERIFIED (code), role ASSUMED.
- `bank0_CODE@0x2FA748`: a 12-entry u32 table `4319824 .. 8154742` (exact 2^(1/12) steps) repeated 21 times, followed by an octave-shift table `17, 16 x12, 15 x12, 14 x12, 13 x12 ...`: a note-to-increment generator (`base[n mod 12] >> shift`). It matches the increment width but is not proven to be the tonewheel frequency source (the Hammond gear tuning of `docs/specs/organ-engine.md` 3.1 is not exact 12-TET). Follow-up 1.
- `bank0_CODE@0x2B9EC8`: 128 u32 values `521 .. 8388607` (MIDI note to 23-bit value, ratio 1.0599, ASSUMED a filter or pitch table, not organ specific).
- `Organ Slot A/B`, `Piano Slot A/B`, `Extern Slot A/B/C`, `Mixer 1/2`, `Sampler` (`@0x27A6D4..`) are UI routing names; they are referenced from menu tables only.
- The 1.29 MiB int16 block at `bank0_CODE@0x2FE000` (see [synth-0x2f-ns4decode-crosscheck](synth-0x2f-ns4decode-crosscheck.md)) was re-tested for a wheel ladder: per-4,096-row autocorrelation peak period is 520 rows for the first ~40 windows then scatters (42, 293, 277, 586, 172, ...), no geometric sequence; **not** a set of 91 wheel recordings. VERIFIED (negative).

## Implications

- **No sampled organ.** `organ.rs` as an additive/physical-model engine is the right architecture class; do not plan an organ sample player.
- **Tonewheel wave:** replace the pure `sin` (and the ad hoc `+0.18 sin 2p + 0.09 sin 3p` of the 12 lowest wheels, ASSUMED) by the firmware wave `sin t - 0.1122 cos 2t - 0.01585 cos 3t - 0.00631 cos 4t - 0.00398 cos 5t` for all wheels, tag `VERIFIED` (table in the PNO Core1 image, max error 1.2e-7) with the caveat that its use for the B3 model is ASSUMED. The second wave (10 harmonics) is a candidate for the "worn wheel" tonewheel mode.
- **Structure:** one shared bank of 92 phase accumulators (not per-key oscillators), mixed by a weight vector per layer. `organ.rs` already has 91 accumulators; adding a 92nd (spare) is free and the weight vector (drawbar x key matrix) is the part that still needs the ARM sender.
- **Vibrato scanner:** the strip program's six triangle LFOs (org-stage-map) and the PNO Core1 triangle + delay-tap stage point to a delay-line scanner; the tap count (19 in the loop) and LFO shapes are the next numbers to compare.
- **Not changed:** no code under `crates/`. TD-04 (contact bounce) stays open; no key-contact or click structure was found in any image.

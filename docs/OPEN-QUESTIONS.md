- **FX biquad table layout (`0x2f730c`, 18x128 `f32`):** rows come in 3 groups of 6 (`A, B, A', B', C, C'`; group 0 idx0 = `1.9496, 0.3493, 1.9440, 0.3436, 0.0093, 0.0094`; group 1 `A` reaches `3.76`, so rows are not plain `a1/a2`). Cascade form, per-group purpose, and idx-to-Hz map are unknown without disassembling the consumer near `0x1bf094`. `fx.rs` uses RBJ designs, not these rows.
- **Stage gain table (`0x2ae5b4`):** 19 entries equal `10^((i-12)/20)` (`-12..+6 dB`, 1 dB steps, exact to 1e-6) plus a `0.0` terminator. Consumer unknown; EQ is `+-15 dB` in 0.25 dB steps, so this is not the EQ gain.

- **Biquad table consumer (disassembly, OS v1.66 `bank0_CODE.bin`, ARM mode):** literal pool `0x1bf094 = 0xc02f730c` (table base). The sender function starting `0x1be108` (pool `0xc02f8b10` = group 1 row 6 + 4, row pointers `+0x1fc`/`+0x3fc` apart) does **not** compute filters: it derives an index with soft-float `double` math (`0x25d2a4`, `0x270a38`, `0x270e18`, ...), then copies table words to the SHARC through the DSP-comm call `0x6ca48` in a loop with stride `0x10`. Coefficients are consumed by SHARC code; a structural scan of the decompressed segments found no DSP image in them (`bank0_CODE`: ARM code `0x0..0x278000` (>0.9 of words with condition `0xE`), then data: float tables, 16-bit PCM-like data at `0x300000..0x438000` (entropy 7.4, first bytes `cc fa 41 fa 41 fa 99 fe`), no 6-byte SHARC word periodicity; `bank1_CODE`: ARM code to `0x8c000`, then pointer tables / low-entropy data). VERIFIED by scan only for those two segments (script in session, heuristic: ARM-condition fraction + byte entropy); not proof that no DSP image exists elsewhere. Later finding: the scan looked for 6-byte ISA words and missed SHARC VISA code, which exists at `0x440000..0x52FFFF` (`docs/research/dsp-image-hunt.md` 5.5). The exact filter form is still unknown. `ASSUMED` hypothesis: per group, rows `A,B,A',B'` are two cascaded sections' feedback terms and `C,C'` feedforward terms; no fit to `a1/a2`, `1-a+b` or DC-gain relations was found. Next: decode the double-math index mapping (idx to Hz/Q) and read the SHARC VISA code in `bank0_CODE@0x440000..0x52FFFF` (see `docs/research/dsp-image-hunt.md`); a SPI flash dump is no longer needed to start.
- **ARM to DSP interface:** the ARM downloads the five DSP images over SPI (`0xC0241C58`, vtable method `0xC0064E7C`) and sends runtime parameters as two-word messages through a memory-mapped EMIFA CS3 port with GPIO flow control (`0xC006CA48`, 904 call sites). Still open: SPI0 vs SPI1, what `0x6200000C`/`0x62000010` connect to, the parameter-id tables and the DSP-side receive path to `DM(0xB00E2)`. See [research/arm-dsp-protocol.md](research/arm-dsp-protocol.md); tool `tools/arm_xref.py`. Real captures from an ARM emulation (strip setter encodings, controller words `DM(0xC1DCC + i)`, `sharc-org --msg-script` replay) and the exact point where the organ drawbar chain stops: [research/arm-fw-emulation.md](research/arm-fw-emulation.md); tools `tools/arm_emu.py`, `tools/arm_capture.py`.
- **ORG DSP receive path:** the DSP has no packet parser; the ARM link is a DMA peek/poke port (3-word frames) writing channel strips at `DM(0xE0000 + 62 k)`. Answered in [arm-param-messages](research/arm-param-messages.md): the ARM message is the 3-word poke `(0x28000000 + 4 w, 0, value)` and the channel bases come from the static initialiser `0xC00002A4`. Open: the controller index to control map (drawbars, key-on), the rule that selects module stages from strip words, and the audio-port DMA that fills the pass inputs. See [dsp-rx-protocol](research/dsp-rx-protocol.md) section 6.
- **PNO Core1 oscillator bank (`0x122620`):** the algorithm is VERIFIED against the oracle ([organ-tonewheel-bank](research/organ-tonewheel-bank.md)); open: its role (B3 tonewheels vs string resonance; [pno-module-chain](research/pno-module-chain.md) finds the ARM installer: the bank is placed in the PNO core 1 call table by the same state machine as the other piano routines, which tips the balance to string resonance), frame rate and absolute pitch, the ARM senders of the weight blocks at DM `0x9566E..0x95949`, the meaning of `kind`/`event` of the slot state machine (`0xC022F060`), and the record that lets the mix stage `0x12268F` run faithfully. Evidence from the booted ARM firmware ([research/arm-organ-messages.md](research/arm-organ-messages.md) section 10): organ ids reach only PNO core 1 (organ model 3 and 4 install the 184 exact 12-TET increments at `DM(0x955B6..0x9566D)`, 1472 of 1472 words equal to the firmware table; replayed into the PNO image they make the bank output non-zero, 736 of 736 words), while the piano ids `Edt_Pno_*` reach only the SMP comm (`DM(0x9403E/0x94046)`, a 1.0 trigger); the Amp ids of the piano and synth layers rewrite the same 184 words through the part routing, so the bank is not organ-exclusive. This favours the organ tonewheel reading over string resonance but is not proof; the drawbar gains stay 0 until the organ weight tables (stubbed SPI downloads) are loaded.

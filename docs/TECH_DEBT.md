## 2. Detailed Technical Debt Registry

### TD-01: GUI Architecture (`egui` vs `nih-plug` VIZIA)
- **Context:** [D11](DECISIONS.md) envisioned unified VST3/CLAP DAW plugin export alongside standalone via `nih-plug`. `crates/nord-gui` was developed with `eframe` and `egui` to deliver rapid cross-platform GUI interaction, crisp OLED graphics, and responsive control surface widgets.
- **Debt:** Currently, the standalone runner is decoupled from DAW plugin host automation interfaces.
- **Remediation Plan:** When implementing `crates/nord-plugin`, either wrap the `egui` canvas using `nih_plug_egui` (unifying standalone and VST3/CLAP UI) or provide standard parameter automation bridges between `nih-plug` parameters and `Stage4PanelState`.

### TD-02: MIDI & Audio Device Selection
- **Context:** `audio.rs` auto-selects the system default CPAL output device and the first available MIDIR input port.
- **Debt:** Users with multiple MIDI controllers (e.g. secondary keyboard or pedalboard) or dedicated ASIO/CoreAudio interfaces cannot switch devices from a GUI settings menu.
- **Remediation Plan:** Introduce a modal settings dialogue or menu bar to list available CPAL audio devices, buffer sizes, and MIDIR input ports.

### TD-03: Piano Engine SFZ Multi-Sample Loader
- **Context:** The Piano engine (`crates/nord-core/src/piano.rs`) provides 120-voice polyphonic velocity tracking, touch curves, and undamped sympathetic resonance, but uses deterministic in-memory wavetable synthesis.
- **Debt:** Clavia's proprietary `.npno` / `CNSP` sample binaries are opaque and compressed without public decoders. Full acoustic realism requires real multi-velocity samples.
- **Remediation Plan:** Implement an open SFZ multi-sample parser and streaming voice reader (e.g. using Salamander Grand or VSCO-2 CE Upright).

### TD-04: Organ Tone Sources, Weights and Contact Bounce

### TD-05: Pre-Allocated Boxed Buffers in `Stage4Engine`
- **Context:** Windows thread stacks are limited to 1 MB by default. Initializing 7 layer delay lines, FDN reverb matrices, and scanner buffers on the stack caused stack overflow (`0xc00000fd`).
- **Debt / Trade-off:** Buffer memory is allocated on the heap inside `Box::new()` during initialization (`Stage4Engine::new()`).
- **Status:** **Accepted Architecture Invariant**. Real-time DSP rendering (`render_frame` / `process_block`) remains strictly zero-allocation and lock-free.
- **Update (2026-11-15, stack footprint):** `Stage4Engine` was 152,128 B (layers by value: Organ 18,184, Piano 11,736, Synth 16,152, `LayerFxChain` 5,808 each) and overflowed Windows CI test stacks as per-layer state grew (`engine::tests_sharing::global_reverb_...` in `nord-core --lib`, earlier `nord-gui --test no_alloc_program_ops`). - **Debt left:** the worst case is about 2.8x over 0.8 ms and misses the 1.6 ms mean / 2.6 ms p99 goal; p99 (4 to 10 ms) is dominated by other processes on the test host, not by the render. What remains is spread thin and mostly cannot shrink without changing the output: the organ drawbar sum is one 792-term dependent float chain per layer (the order is part of the output, about 0.25 ms for two layers), the 7 FX racks cost about 0.65 ms (cabinet FIR, delay, chorus, reverb, EQ), the synth voices about 0.15 ms per layer (filter recursion, 7-oscillator supersaw), `sinf` about 0.15 ms. Options that change bits, and so need a new golden hash and a measured error bound: a table or polynomial sine for the 91 wheels, batching the 7 cabinet FIRs across layers in SIMD, rendering layers on several threads (needs a lock-free pool).
- **Update 2026-11-17 (D161):** the firmware FX ports are a separate, larger cost: Horizon Whl on 480 frame blocks runs 12 to 15 ms with `--firmware-fx` against 0.6 ms with the engine FX (each of 7 racks runs a firmware reverb, about 1 ms per rack and block; [gui-audio-glitches](research/gui-audio-glitches.md)). `E40` fast path (bit-identical, about 5 percent) and the opt-in `--fx-idle-skip` (Scene I: 2.7 to 3.8 ms) are in; a scene that plays seven layers with firmware reverbs is still over the budget.
- **Update 2026-11-18 (D163):** the firmware Mod 2 became the default, but the bench worst case sets Mod 2 by type and never runs it. `ns4 bench --scenario worst-fw-chorus` and `worst-fw-spin` set the raw words on all 7 chains (`bench_fw_mod2.rs`; release, 2000 blocks, 128 frames, 4 outputs, this machine, 3 runs each): `worst` (engine Chorus) mean 1.20 to 1.21 ms (hash `0xbb458dfcf2a14742`), `worst-fw-chorus` 1.58 to 2.28 ms (typical 1.58, hash `0x0d435a065a306c84`), `worst-fw-spin` 2.02 to 2.40 ms (hash `0x155c919648dad2f8`). That is about +0.05 ms (CHOR) and +0.11 to +0.17 ms (SPIN) per active chain and block; an independent measurement gave +0.03 to +0.09 ms per chain, about 300 ns per frame for CHOR and 750 ns for SPIN against about 51 ns for the engine Mod 2. A program that loads Mod 2 on all 7 layers stays real time on this machine but moves the worst case further from the 0.8 ms figure. See TD-18.
- **Update 2026-11-19 (D167):** with the new defaults (firmware Mod 2, Touch, arp walk, morph) the real cpal callback on A:16 Horizon Whl (Scene I, 6 keys, arp up, 480 frame device buffer) runs at 25 to 30 percent load with no late block (`nd-matrix-1 --audio-probe`), so the defaults are not render bound on this host; the opt-in `--firmware-fx` still is (load 86 to 88 percent, 115 to 198 of 1200 blocks late). The crackle that remained came from the scheduler (cpal never raised the callback thread, fixed) and from the master bus hard clamp on hot patches; see [gui-audio-glitches](research/gui-audio-glitches.md) section 6.
- **Update 2026-11-19 (firmware reverb speed):** the firmware reverb port is about 1.3x cheaper, bit-identical (`E40` mul through the f64 product with the integer path only on a 32 bit tie, `E40` add within 20 binades without the error-term test, both inlined, one window search per paired access; pinned by `tests_fw_reverb_pinned.rs`, 29 type / colour hashes from the old implementation). About 0.8 to 0.9 ms per reverb and 480 frame block on this host (was 1.0 to 1.1); the 2x goal was not reached. `lto = "fat"` + `codegen-units = 1` would give 1.15 to 1.2x more (not adopted, owner decision). [fw-reverb-speed](research/fw-reverb-speed.md).
- **Remediation Plan:** (1) keep `ns4 bench --scenario worst|typical|idle` and its hash as the gate for any optimisation; (2) if the worst case must reach 0.8 ms, take the bit-changing options above one at a time with an error bound and `VERIFIED` / `EMPIRICAL` tags; (3) the PRD table now states the budget per scenario (typical met, worst case not).
- **Status:** Partly resolved (typical case within budget, worst case real time at about 1.2x, over the 0.8 ms figure).

### TD-15: B3 Bass Firmware Stage Is Not Real Time

- **Description:** The opt-in B3 Bass stage (`organ/b3_bass_stage.rs`, D71) and Farfisa stage (D74) run decoded firmware routines on a 40 bit float SHARC machine (`organ/b3_bass_fw/`, 24,000 calls per second of audio, 2,283 (Bass) and 1,034 (Farfisa) instructions per call). The row interpreter cost 3.3 to 3.6 s (Bass) and about 2 s (Farfisa) of CPU per second of audio.
- **Work done (D192, [organ-farfisa-bass](research/organ-farfisa-bass.md) s18):** instructions are compiled once into a flat in place program (`compile.rs`, `fastexec.rs`), zero operands and `float` / `PASS` take 64 bit paths, the float rounding has no data dependent branch. Bit identical (whole machine state compared after every call, goldens and output hashes unchanged). Measured on this host, release, three keys: Bass 1.82 to 1.91 s to 0.63 to 0.65 s, Farfisa 1.34 to 1.36 s to 0.43 to 0.48 s (stage alone: 0.27 s, the other 0.16 s is the `FarfisaWheels` ring) of CPU per second of audio. `ns4 bench --scenario organ-bass` / `organ-farfisa` measure the block cost.
- **Impact:** Farfisa (about 0.6 to 0.9 ms per block with its ring) sits at the 0.8 ms block budget; Bass (stage alone about 1.0 to 1.4 ms) is real time alone but a full program with it is over the budget on a shared host. Both stay opt-in (D22); the 6 programs that use them are still offline by default.
- **Work done (D198, [organ-farfisa-bass](research/organ-farfisa-bass.md) s19):** the planner (`plan.rs`) compiles the instructions that still used the reference path (cycles through split compute / commit halves, conditional ALU items), and the compiled programs are emitted as straight line Rust (`native_gen.rs` writes `native_bass_gen.rs`, `native_bass_proc.rs`, `native_farfisa.rs`; no dispatch, literal operands, fixed size DM). Bit identical: whole machine state compared after every call (600 Bass, 300 Farfisa calls), output hashes of `organ_fw_bench` and the three `ns4 bench` scenarios unchanged. Bass about 0.65 to 0.4 s, Farfisa about 0.45 to 0.25 s of CPU per second of audio (shared host, ranges in s19).
- **Work done (D208, [organ-farfisa-bass](research/organ-farfisa-bass.md) s20):** the three D198 ideas were measured and dropped. Unrolling the 22 and 10 pass loops made a call 2x slower (16.9 to 36 us; the index registers are loaded from DM pointers, so no address becomes a literal); no pass of those loops is an identity on registers, flags and DM, with keys or without (`b3_bass_fw/probe.rs`), so unheld voices cannot be skipped bit identically; the float add and multiply are 2.4 to 2.9 us of the 9.5 us generator call, so SIMD saves at most about 6 percent. Code and hashes unchanged.
- **Remediation Plan (remaining):** Bass stage alone is about 0.96 to 1.1 ms per block (0.36 to 0.41 s of CPU per second of audio) against the 0.8 ms budget of the whole engine. (1) Registers in locals: the generated routines keep the data and index registers in local variables so LLVM holds them in machine registers across items (the register file traffic is the largest part left); (2) a second core behind a lock free queue; (3) a closed form of the Farfisa processor (Farfisa alone is inside the budget). Dropped by measurement (D208): unrolling, skipping unheld voices, SIMD over the PEs.
- **Status:** Partly resolved (Farfisa at the block budget; Bass about 1.6x faster than D192 but still over it; D208 closed unrolling, skipping and SIMD)

### TD-18: Firmware Mod 2 Allocates Lazily and Costs More Than the Engine Mod 2
- **Description:** Since D163 the firmware Mod 2 (`FirmwareFx::DEFAULT.mod2`) runs for every program that carries the raw `kFx2Type` / `kFx2RateClkDiv` words. The stage boxes (`FwMod2Stage`, `FwLawStage`, `FwVibeStage`, several KB each) used to be created with `Box::new` inside `process_frame` the first time a type was used and again, with a free, on every type change; the stage latency is fixed at 4 frames (83 us at 48 kHz) and the cost is 0.05 to 0.17 ms per active chain and 128 frame block (TD-14, D163).
- **Resolved 2026-11-19 (D167), allocation part:** `LayerFxChain::reserve_firmware_stages` allocates every Mod 1 / Mod 2 stage box once (`Stage4Engine::reserve_audio_stages`, called by `standalone_engine`), and `process_fw_mod2` re-initialises a parked box in place with the stage constructor (built on the stack, so no heap call and no free). Output is bit-identical (`fx::tests_reserve_stages` compares 12 type switches bit for bit with the lazy path). `crates/nord-gui/tests/no_alloc_fx_stages.rs` (counting allocator) shows 0 allocator calls for ten `LoadProgram`s with different Mod 1 / Mod 2 types on a reserved engine against more than 20 on a plain one. Measured cost of the old lazy builds (`ns4 bench --gui --reload 300 --reload-pool 59`, 128 frames, Scene II, 10 keys): the first block after a load costs 0.03 to 0.07 ms more than the next two on average and 0.45 to 1.4 ms at worst, against a 2.67 ms deadline, so it was a small risk (heap lock contention with the GUI thread) and not the main crackle source.
- **Remaining:** the 4 frame latency is part of the firmware routine and is not compensated against the dry path. The panel's Mod 2 AMOUNT knob sent the whole Mod 2 edit set, which clears the firmware words (PR 524 changes the panel to send only the amount); the plugin runs the engine Mod 2 for the same reason (`sync_to_engine` clears the words every block) and does not call `reserve_audio_stages` yet. The opt-in firmware reverb (`FwReverb::new`, `FwReverbMulti`), compressor (`fw_comp`) and A-PAN / TREM stage are still built lazily on first use or type change; build them in `reserve_firmware_stages` the same way if they become default. Per-frame cost of CHOR and SPIN (0.3 and 0.75 us per frame against 0.05 us for the engine Mod 2) is unchanged; a faster executor needs the same work as TD-15.
- **Status:** Partly resolved (allocation and free off the audio path for the default stages; cost and latency open).

### TD-19: Organ and Synth SOLO Do Nothing in the Engine

- **Description:** Holding the Organ ON button toggles `organ_ui.solo` and the SOLO legend LED (`panel/organ_strip.rs`, test `hold_on_on_button_toggles_solo` only checks the flag); the Synth strip's SOLO legend (`bay_synth/strip.rs`) is likewise cosmetic. Piano SOLO sends `PianoEdit::SceneMask` (`piano_logic::solo_start` / `solo_end`: only that section sounds while ON is held, the previous scene returns on release).
- **Reproduction:** `cargo test -p nord-gui --lib hold_on_on_button_toggles_solo`; in the GUI hold Organ ON for 0.7 s with a Piano layer playing: the SOLO LED lights, the Piano keeps sounding. The Organ flag also latches (toggle) where Piano SOLO lasts only while held.
- **Remediation Plan:** reuse `PianoEdit::SceneMask` (organ layers are bits 0..1, Piano 2..3, Synth 4..6): `solo_start` / `solo_end` per section driven by the held state of the ON button, with tests that the mask is `organ_bits` while held and the saved scene returns on release.
- **Status:** Open.

### TD-20: Panel Fx View Does Not Mirror Mod 2 Variation After a Program Load

- **Description:** `ui_state/fx/echo.rs` `StateEcho` has no `mod2_variation` (nor the raw Mod 2 words); `Stage4PanelState` has no such legacy field, so `apply_program` cannot reach `ChainUi::mod2_variation`. Every Mod 1 / Mod 2 control now sends only its own edit (`bay_effects/mod_touch.rs`; tests `every_mod_control_sends_only_its_own_edits`, `mod_amount_knob_sends_only_the_amount_and_keeps_a_loaded_mod2`), so a loaded variation is no longer overwritten by an unrelated knob. Still open: the VAR legend of a loaded CHOR variation shows off, and a Shift + selector toggle writes `true` from that stale view (the engine flag is then inverted relative to what is printed); a type or rate edit legitimately clears the Mod 2 firmware raw words (by design: the edit must be audible).
- **Remediation Plan:** read the loaded chain's variation flag into `ChainUi` on program load (telemetry or a `StateEcho` field), with a test that a loaded variation shows lit and survives a rate edit.
- **Status:** Open.

### TD-21: A Loaded Program Is Not Mirrored Into Host Parameters and Is Not Persisted

- **Description:** D218 adds the load path (top bar, queue to the audio thread, per-group hold). Remaining gaps: (a) touching one host parameter of a group collapses that whole group to host values; (b) the editor panel and host automation lanes still show host values, not the loaded program (the panel shows the global Touch, not the per-layer one); (c) the loaded program is not stored in project state, so a reloaded project plays from host parameters only; (d) `LoadPreset` is unmapped; (e) an OS update file applies once per process; (f) loading in Reaper and Bitwig is not verified by hand (FL Studio is, see `HOST_COMPATIBILITY.md` 7.9).
- **Impact:** After touching a control the program's other values in that group go away; reopening a project loses the program until it is loaded again.
- **Remediation Plan:** (1) push program values into the host parameters on load (`begin_set/set/end_set` from the GUI thread) so panel, automation and persistence agree and the hold can go; (2) persist the loaded program path or bytes in `Stage4Params`; (3) map `LoadPreset`; (4) hand-test in FL Studio, Reaper and Ableton and record it in `docs/HOST_COMPATIBILITY.md`.
- **Status:** Partly resolved by D218 (loader and hold). (c) is resolved for programs of the saved sound library: `library_program` is a host parameter and the library worker (`auto_library.rs`) reloads it with the project; a program opened by hand in the editor is still not persisted. The other items are Open.
